# 문서 작성 가이드

적용 대상: `notes/` 아래 모든 문서와 풀이 파일의 Javadoc 주석. 채팅 말투에는 적용하지 않는다.

독자는 "내용을 다 잊은 몇 주 뒤의 나"다. 면접 전날 빠르게 훑는 상황을 기준으로 쓴다. 그래서 이 가이드의 기준은 하나다: **다시 읽었을 때 해석이 한 번에 끝나는가.**

---

## 개인 정보 (커밋되는 모든 파일)

git에 올라가는 파일(`notes/`, `src/`, README)에는 개인 정보를 쓰지 않는다. 이름, 이메일, 계정, 회사명 등이 대상이다.

**회사명은 전 직장뿐 아니라 지원한 회사, 면접 보는 회사도 포함한다 (2026-08-16 신설).** 
저장소는 공개이고 프로필에 링크가 걸려 있으므로, 어느 회사의 어느 단계를 언제 밟았는지가 전부 읽힌다. 
다른 회사도 보고 그 회사도 본다. 학습 기록에 필요한 것은 "면접 음성 연습 15분"이라는 사실이지 상대가 누구인지가 아니다. 회사명 대신 일반 명사를 쓴다.
예를 들어 특정 회사 이름을 붙인 연습 세션은 "면접 음성 세션"으로, 특정 회사의 채용 단계는 "리크루터 스크리닝"으로 적는다. 
**이 규칙 문서 자체에도 실제 회사명을 예시로 넣지 않는다.**

**건강 정보도 쓰지 않는다 (2026-08-16 신설).** "5일 병결"까지는 일정 기록이지만 증상과 진단은 의료 정보다. 
미국 채용에서 고용주가 물어보는 것 자체가 금지된 항목이므로 저장소가 자진해서 알려줄 이유가 없다. 배경은 memory에만 남긴다. 
인용이 필요하면 `[name]`, `[email]` 플레이스홀더로 바꾼다. 예외: `CLAUDE.md`는 gitignore에 있어 커밋되지 않으므로 학습자 프로필 등 개인 데이터를 둘 수 있다.

## 표기 규칙 (쓸 때 지키는 것)

- em dash(—)를 쓰지 않는다. 쉼표, 마침표, 괄호로 푼다.
- 중점(·)으로 단어를 이어 붙이지 않는다. 쉼표로 나열한다.
- 용어가 처음 나오면 괄호로 원어와 한 줄 뜻을 붙인다. 형식: `불변식(invariant, 루프 내내 항상 참인 성질)`. 두 번째부터는 용어만 쓴다.
- 노트 본문은 "~다" 평서형으로 쓴다. 대화체("~야", "~잖아")를 섞지 않는다.
- 노트의 화자는 나 자신이다 (2026-08-16 신설). 나를 가리킬 때는 주어를 생략하고, 꼭 필요하면 "내가"를 쓴다. "사용자", "본인", "학습자" 같은 3인칭은 쓰지 않는다. 코치를 가리킬 때만 "코치"를 쓴다. 코치가 대신 적어 주더라도 몇 주 뒤에 읽는 사람은 나이므로, 관찰 일지가 아니라 내 기록이어야 한다.
- 문제는 `번호 + 영문 제목`으로 부른다. 예: "49 Group Anagrams". "그 문제", "어제 그거"처럼 대명사로 부르지 않는다.
- 복잡도는 O 표기로, 실측은 ms 단위로 쓰고 둘을 섞지 않는다. "빠르다"라고만 쓰지 않는다.
- 볼드를 쓰지 않는다 (2026-08-16 신설). 일일 노트에서 볼드가 파일당 10~21개까지 늘어 강조가 강조 구실을 못 했다. 
- 훑을 때의 앵커는 불릿 요약 줄이 맡는다. 코드와 식별자는 백틱으로 구분되므로 볼드가 따로 필요하지 않다.
- 일일 노트의 항목은 요약 한 줄을 쓰고 상세를 한 단계 들여쓴다 (2026-08-16 신설). 요약만 훑어 그날 무슨 일이 있었는지 파악할 수 있어야 한다.

```
- 공간복잡도를 코드와 대조하지 않고 적었다
  - 19에서 ArrayList에 노드 전부를 담고도 공간 O(1)로 기재했다
  - 처방은 복잡도 칸을 채울 때 코드의 new를 전부 세는 것이다
```

## 편집 체크리스트 (고칠 때 훑는 것)

글을 다 쓴 뒤 아래 여섯 개만 훑는다.

1. 추상어가 구체적인 동작을 가리지 않는가
2. "좋다", "빠르다", "유용하다"로 끝난 문장에 무엇이 어떻게 달라지는지 적혀 있는가
3. 문장의 주어가 있는가 (누가 또는 무엇이, 어떤 조건에서, 뭘 하는지)
4. 성능이나 난이도 주장에 근거가 붙어 있는가
5. 비유가 실제 용어 없이 혼자 돌아다니지 않는가
6. 같은 개념 설명이 두 문서에 중복되지 않는가

## 각 항목 설명과 우리 예시

### 1. 추상어와 빈 개념어

"효율성", "안정성", "유연성"처럼 빼도 문장이 그대로인 말은 뺀다. 동작이 있으면 동작을 쓴다.

```
✗  computeIfAbsent를 쓰면 효율적이다
✓  computeIfAbsent를 쓰면 버킷 조회가 2번에서 1번으로 준다
```

### 2. 효과는 변화량으로 쓴다

```
✗  사전 사이징을 하면 성능에 도움이 된다
✓  사전 사이징을 하면 리해싱(전체 재배치)이 0번이 된다. 10만 개 기준 재배치 약 13만 회가 사라진다
```

### 3. 주어를 세운다

"검증되어야 한다" 같은 주어 없는 문장은 누가 뭘 하는지 안 보인다.

```
✗  중복 여부가 확인되어야 한다
✓  add()가 false를 반환하면 그 값은 이미 Set에 있던 것이다
```

### 4. 주장에는 근거를 남긴다

"대체로", "~일 수 있다"를 금지하지 않는다. 불확실한 것을 단정하는 쪽이 더 나쁘다. 대신 무엇을 보고 판단했는지 남긴다. 매번 수치까지는 필요 없고, 판단의 출처면 된다.

```
✗  정렬 키가 더 빠르다
✓  정렬 키가 실측에서는 더 빠르게 나오기도 한다 (k ≤ 100이라 log k 페널티가 작고,
   원시 배열 정렬은 박싱이 없다. 49 제출에서 직접 비교는 아직 안 함)
```

실측 ms를 적을 때는 조건을 같이 적는다. "11ms"가 아니라 "49 제출 기준 11ms (고정 26칸 키)".

### 5. 비유는 용어와 반드시 같이 쓴다

비유는 이 노트의 교재 역할에 필요해서 금지하지 않는다. 다만 비유만 있으면 몇 주 뒤에는 원래 용어가 기억 안 나서 한 번 더 해석해야 한다. 
규칙: **비유가 나오는 문장에는 실제 용어가 같이 있어야 한다.**

```
✗  수첩이 꽉 차면 더 큰 수첩으로 옮겨 적는다
✓  버킷 배열이 75%를 넘으면 2배 크기로 리해싱한다. 수첩을 더 큰 수첩으로 옮겨 적는 셈이다
```

정착한 비유 대응표: 수첩 = 해시맵, 칸/양동이 = 버킷, 이사 = 리해싱, 포장 = 박싱, 갈아입히기 = 배열을 String 키로 변환.

### 6. 같은 설명을 두 곳에 쓰지 않는다

개념 설명의 본체는 `concepts.md` 한 곳에만 둔다. 일일 노트에는 그날의 결과, 실수, 그리고 "concepts.md 몇 번 섹션"이라는 참조만 쓴다. 복습할 때 두 버전이 미묘하게 다르면 어느 쪽이 맞는지 다시 확인하게 되기 때문이다.

### 7. 실수 기록에는 재현 조건을 남긴다

"음수 케이스를 놓쳤다"만 쓰면 나중에 뭘 놓쳤는지 재현이 안 된다. 어떤 입력에서, 왜 터졌는지까지 쓴다.

```
✗  음수 케이스를 놓쳤다
✓  nums[i] <= target 필터가 nums=[-2,-3], target=-5에서 두 원소를 모두 걸러서 빈 배열을 반환했다.
   원인: 제약 조건(-10^9 <= nums[i])을 읽지 않고 값을 양수로 가정함
```

### 8. 표와 문장의 역할을 나눈다

표는 비교와 선택 기준("언제 뭘 쓰나")에만 쓴다. 이유와 과정 설명을 표 칸에 욱여넣지 않고 표 앞뒤 문장으로 쓴다.
