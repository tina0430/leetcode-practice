# 개념 정리 노트

문제 풀며 배운 개념 누적 정리. **⭐ = 필수(먼저 소화)**, **🔍 = 딥한 최적화(급하면 스킵하고 나중에 와도 됨)**.

## 1. 문제 풀이 6단계 ⭐

문제를 열자마자 코딩부터 시작하면 안 된다. 요리로 치면 레시피도 안 읽고 불부터 켜는 것. 아래 6단계를 순서대로 밟는다. 1~3단계는 "문제 읽기", 4~5단계는 "풀이 설계", 6단계는 "검증"이다. **읽기가 끝나기 전에 설계를 시작하지 않는 것**이 핵심 규칙.

### 1단계. 입출력 정의 — "뭘 받아서 뭘 돌려주는 거지?"

당연해 보이지만 여기서 이미 중요한 결정이 갈린다. Two Sum이 좋은 예:
- 반환하는 게 "두 수의 **값**"이 아니라 "두 수의 **인덱스**(몇 번째 칸인지)"다.
- 인덱스를 반환해야 한다 → 배열을 정렬하면 인덱스가 뒤섞인다 → **"정렬은 못 쓰겠구나"** 라는 판단이 코딩 전에 나온다.
- 인덱스를 나중에 알아야 한다 → **"인덱스를 어딘가 보관해야겠구나"** 도 여기서 나온다.

이렇게 반환형 하나만 정확히 봐도 설계의 절반이 정해진다.

### 2단계. 제약 조건 읽기 — 출제자가 미리 알려주는 힌트

LeetCode 문제 페이지 맨 아래 **Constraints**(제약 조건) 항목. 대부분 안 읽고 넘어가는데, 사실 여기가 정보 밀도가 제일 높다. 제약 조건은 세 종류의 정보를 준다.

**① 값의 범위** — 예: `-10^9 <= nums[i] <= 10^9`
- 마이너스가 보이면 → **음수가 들어온다.** "값은 양수겠지" 같은 상상 금지.
- 값이 10억까지 크면 → "값을 배열 칸 번호로 쓰는 방법"(카운팅 배열)은 불가능. 10억 칸짜리 배열은 못 만드니까. → 해시맵을 쓰라는 신호.
- 반대로 "소문자 알파벳만"이면 종류가 26개뿐 → 배열로 셀 수 있다는 신호.

**② 입력 크기** — 예: `n <= 10^4`
이건 **시간 예산표**다. 컴퓨터가 1초에 대략 1억 번(10^8) 연산한다고 잡으면:

| n의 최대 | 총 연산 횟수 계산 | 결론 |
|---|---|---|
| 10^4 (1만) | O(n²)이면 10^8 | 아슬아슬 통과. 브루트포스도 되긴 함 |
| 10^5 (10만) | O(n²)이면 10^10 | 100초. 탈락. O(n log n) 이하로 풀라는 뜻 |
| 10^6 (100만) | O(n log n)이면 약 2×10^7 | 이 정도까지만 허용 |

즉 n만 봐도 "출제자가 어떤 복잡도의 풀이를 기대하는지" 역산이 된다.

**③ 보장 사항** — 예: "정답은 정확히 하나 존재한다"
"정답이 없으면 어쩌지?", "정답이 여러 개면 뭘 반환하지?" 같은 걱정을 안 해도 된다는 공식 약속. 예외 처리 범위가 줄어든다.

> **실수 사례 (Two Sum에서 직접 겪음):** `if (nums[i] <= target)` 필터를 넣었다가 틀렸다. "target보다 큰 수는 짝이 될 리 없다"고 생각했지만, 그건 값이 전부 양수일 때만 참이다. 음수 세계에선 `-2 + -3 = -5`처럼 target(-5)보다 큰 두 수가 짝이 된다. **제약 조건에 근거가 없는 필터/가지치기(경우의 수 쳐내기)는 금지.** 게다가 그 필터는 맞았어도 복잡도를 못 바꾸는(어차피 O(n)) 최적화였다 — 이득 없이 위험만 추가한 셈.

### 3단계. 예제를 손으로 풀어본다 — 예제는 함정 경고장이다

예제는 "문제 이해했나 확인용"이 아니다. **출제자가 일부러 함정 케이스를 예제에 심어둔다.** Two Sum의 예제 3번이 `[3,3], target=6`인 건 우연이 아니라 "중복 값 조심해"라는 경고다. 예제를 손으로 따라가며 "내 방식이 이 케이스에서 정확히 뭘 하지?"를 시뮬레이션한다. 여기서 발견한 함정이 6단계의 테스트 케이스가 된다.

### 4단계. 브루트포스 먼저 + 복잡도 (⭐⭐ 내 최대 약점, 집중)

**브루트포스(brute force) = "무식하게 다 해보기".** 특정 기법의 이름이 아니라, 이 질문의 답이다:

> **"문제의 정의를 그~대로, 아무 머리도 안 쓰고 확인하려면, 뭘 다 해봐야 하지?"**

세 문제로 연습:

| 문제 | 정의 그대로 확인하려면? | 복잡도 |
|---|---|---|
| Two Sum: "합이 target인 **쌍**이 있나" | 모든 쌍을 만들어 더해본다 | 쌍의 개수 = O(n²) |
| Contains Duplicate: "**같은 두 원소**가 있나" | 모든 쌍을 비교해본다 | 역시 모든 쌍 = O(n²) |
| Valid Anagram: "t는 s를 재배열한 건가" | s의 글자 하나마다 t 전체를 뒤져 지워본다 | 글자 n개 × 매번 n칸 = O(n²) |

패턴: **"~한 게 있나?"류 문제의 브루트포스는 거의 항상 "후보 전부 나열"이고, 후보가 쌍(2개 조합)이면 O(n²)이다.**

복잡도 계산은 규칙 하나만 기억하면 된다:

> **겹친 반복문은 곱한다.**
> - n번 도는 루프 안에 또 n번 도는 루프 → n × n = **O(n²)**
> - n번 도는 루프 안에서 매번 O(1)짜리 일(해시맵 조회 등) → n × 1 = **O(n)**
> - n번 도는 루프가 나란히 두 개(중첩 아님) → n + n = 2n = **O(n)** (상수배는 떼고 말한다)

**주의 (217에서 직접 헷갈린 것):** "브루트포스: O(n)"이라고 적었는데, O(n)은 브루트포스가 아니라 Set을 쓴 **최종 풀이**의 복잡도였다. 브루트포스(모든 쌍 비교)는 O(n²). 두 개는 완전히 다른 것이고, 4단계에 적을 건 전자다.

왜 굳이 브루트포스를 먼저 말하나? 두 가지 이유:
1. **기준선**: 최적화가 막혀도 돌아올 정답이 있다. 면접에서 "일단 O(n²)로는 풀립니다"라고 깔아두면 최소 점수는 확보.
2. **공격 목표**: 5단계는 "브루트포스의 어디가 낭비인가"를 찾는 단계다. 브루트포스가 없으면 공격할 대상도 없다.

### 5단계. 병목 찾기 → 도구 선택

**병목(bottleneck) = 전체를 느리게 만드는 가장 낭비스러운 부분.** 브루트포스 코드를 머릿속에 놓고 "어느 부분이 반복적으로 쓸데없는 일을 하지?"를 지목한다.

Two Sum의 경우: 안쪽 루프가 하는 일 = "내 짝이 있나 배열을 처음부터 다시 뒤지기". 이게 낭비다. → "이 '찾기'를 더 싸게 하는 도구가 있나?" → 배열 탐색 O(n)을 해시맵 조회 O(1)로 교체 → 전체가 O(n²)에서 O(n)으로.

**자료구조는 문제 보고 찍는 게 아니라 병목에서 역산해서 고르는 것.** 다만 솔직한 진실 하나 — 이 단계는 "머리로 생각해내는" 게 아니라 **도구를 미리 알아야 나온다.** 해시맵을 모르면 해시맵이 안 떠오르는 게 당연하다. 좋은 소식은 면접 문제 대부분이 15~20개 패턴(해시맵, 투 포인터, 슬라이딩 윈도우, 스택, 이진 탐색, BFS/DFS, DP 등 — src/ 폴더 구조가 그 목록)으로 커버된다는 것. 공부 = 이 도구들을 하나씩 수집해서 병목과 매칭하는 훈련.

### 6단계. 검증 + 복잡도 진술

코딩이 끝나면: 예제 전부 + 3단계에서 발견한 함정 케이스(음수, 중복, 빈 입력, 길이 다름 등)를 손으로 또는 main()으로 통과시킨다. 마지막으로 "시간 O(n), 공간 O(n)입니다"라고 소리 내어 말할 수 있어야 끝난 것이다.

## 2. HashMap / HashSet — 내부에서 무슨 일이 일어나나 ⭐

### 핵심 아이디어: "아무 키로나 즉시 접근"

배열은 "3번 칸 주세요" 하면 즉시 나온다(O(1)). 근데 칸 번호를 알아야만 쓸 수 있다. 해시맵은 이걸 확장한 것: **"apple 주세요"처럼 아무 키로나 즉시(평균 O(1)) 찾게 해주는 자료구조.**

### 어떻게 가능한가: 키를 칸 번호로 변환한다

해시맵의 속은 사실 그냥 배열이다(**버킷 배열**이라고 부른다. bucket = 물건 담는 양동이 = 배열의 한 칸). 저장/조회 과정:

```
1. 키를 해시 함수에 넣어 정수를 얻는다        "apple".hashCode() → 93029210
2. 배열 크기로 나눈 나머지 = 칸 번호           93029210 % 16 → 10
3. 그 칸(버킷)에 넣거나 꺼낸다                buckets[10]
```

몇 개가 들어있든 탐색 없이 계산 한 번으로 칸에 직행하니까 O(1)이다. "키 → 숫자 → 칸 번호" 변환이 전부다.

### 충돌: 다른 키가 같은 칸에 떨어지면?

`% 16` 같은 나머지 연산이라 다른 키가 같은 칸 번호를 받을 수 있다(**충돌, collision**). 자바의 처리:
- 같은 칸에 온 애들을 **연결 리스트로 줄줄이 매단다**(체이닝). 조회할 땐 그 줄에서 키를 하나씩 비교.
- 한 칸의 줄이 너무 길어지면(8개 이상) 트리 구조로 바꿔서 최악에도 O(log n)으로 방어.
- 그래서 **평균 O(1), 최악 O(log n)**. 면접에선 "평균 O(1)"이라고 답하면 된다.

### 리사이징: 수첩이 꽉 차면 더 큰 수첩으로

- 버킷 배열은 **기본 16칸으로 시작**한다.
- 항목 수가 칸 수의 **75%** (이 비율을 load factor라고 부른다)를 넘으면 → 배열을 **2배로 키우고, 기존 항목 전부를 새 배열에 재배치**한다(**리해싱**).
- 왜 전부 재배치? 칸 번호가 `해시값 % 배열크기`인데 배열 크기가 바뀌면 **모든 항목의 칸 번호가 달라지기 때문.** 항목 m개면 O(m)짜리 이사 작업이다.
- HashSet은 "값 없이 키만 있는 HashMap"이다. 내부 원리 완전히 동일.

> 면접 단골 질문 "HashMap 내부 구조 설명해보세요"의 모범 답안 = 위 내용을 순서대로: **해시 함수 → 버킷 인덱스 → 충돌 처리(체이닝, 트리화) → 리사이징(16칸, 75%, 2배)**.

### 자료구조 선택 기준표 ⭐

| 상황 | 선택 | 이유 |
|---|---|---|
| 키 종류가 적고 미리 안다 (소문자 26개 등) | **배열** `int[26]` | 해시 계산도 충돌도 없는 해시맵의 상위호환. `c - 'a'`로 칸 번호 직행 |
| 키 범위가 크다 (±10^9 등) | HashMap | 배열로는 칸을 못 만드니까 |
| 값 없이 "있냐 없냐"만 필요 | HashSet | |
| 넣은 순서 유지 필요 | LinkedHashMap | |
| 키가 정렬된 상태로 필요 | TreeMap | 대신 조회가 O(log n) |

## 3. Map/Set 필수 API — 언제 뭘 쓰나 ⭐

전부 **Java 8**(2014)에서 람다와 함께 들어온 것들. 공통 목표는 "조회 두세 번 할 일을 한 번으로".

### `set.add(x)`는 성공 여부를 알려준다

Set은 중복을 거부한다. 그래서 `add`는 **"넣는 데 성공했나"를 boolean으로 반환**한다:

```java
exist.add(3);   // true  — 새로 들어감
exist.add(3);   // false — 이미 있어서 거절됨
```

이걸 알면 "있나 확인(contains) → 없으면 넣기(add)" 조회 2번이, "넣어보고 거절당하면 = 이미 있던 것" 조회 1번이 된다:

```java
if (!exist.add(num)) return true;   // 중복 발견!
```

### 4형제 비교표

| API | 한 문장 요약 | 대표 사용처 |
|---|---|---|
| `getOrDefault(k, 기본값)` | "없으면 기본값 셈 치고 읽기" (맵은 안 바뀜) | 카운팅: `m.put(c, m.getOrDefault(c,0)+1)` |
| `putIfAbsent(k, v)` | "없을 때만 넣기" (값이 이미 손에 있을 때) | 드물다. 아래 함정 참고 |
| `computeIfAbsent(k, 람다)` | "없으면 만들어 넣고, 그 값을 돌려줘" | **그룹핑 표준**: `m.computeIfAbsent(k, x -> new ArrayList<>()).add(v)` |
| `merge(k, 1, Integer::sum)` | "없으면 1, 있으면 기존값+1" | 카운팅 한 줄 (347에서 실전 투입 예정) |

### putIfAbsent의 함정 (49에서 직접 겪음)

```java
map.putIfAbsent(key, new ArrayList<>());  // ① 조회 1번째
map.get(key).add(x);                      // ② 조회 2번째
```

문제 두 개: ①과 ②가 **같은 칸을 두 번 찾아간다.** 그리고 자바는 메서드 호출 전에 인자부터 계산하므로, **키가 이미 있어도 `new ArrayList<>()`가 일단 만들어졌다 버려진다.** 항목 1만 개면 쓰레기 리스트 수천 개.

`computeIfAbsent`는 둘 다 해결: 칸을 한 번만 찾아가고, 두 번째 인자가 값이 아니라 **람다**("필요할 때 실행할 레시피")라서 키가 없을 때만 리스트가 만들어진다(이걸 **지연 평가** — 미리 만들지 않고 필요한 순간에 만들기 — 라고 한다). 게다가 값을 반환해줘서 `.add()`를 바로 이어 붙일 수 있다.

## 4. char와 String의 정체 ⭐

### char는 글자 옷을 입은 숫자다

자바의 `char`는 **16비트 정수**다. `'a'`라고 쓰면 실제 저장되는 건 숫자 97이다.

```java
(int) 'a'         // → 97
(char) 98         // → 'b'
(char) ('a' + 1)  // → 'b'  ('a' 다음 글자)
(char) 3          // → 화면에 안 보이는 값이지만 완전히 합법인 char
```

여기서 나오는 필수 관용구: **`c - 'a'`** = 소문자를 0~25번 칸 번호로 바꾸기. ('a'-'a'=0, 'b'-'a'=1, ... 'z'-'a'=25) → `int[26]` 카운팅 배열의 열쇠.

### 함정: char는 계산식에 들어가는 순간 int가 된다

`'a' + j`의 결과 타입은 char가 아니라 **int**다(자바가 자동으로 승격시킴). 그래서 `List<Character>`에 `add('a' + j)`하면 컴파일 에러 — int를 Character로는 자동 변환 안 해준다. 해결은 명시적 캐스팅:

```java
(char) ('a' + j)   // OK. 괄호로 전체를 감싸야 함
(char) 'a' + j     // 함정! 'a'만 캐스팅되고 결과는 도로 int
```

### String은 "내용으로 비교되는 불변 컨테이너"다

String의 정체 = **내부에 char 배열을 품은 불변(만든 뒤 수정 불가) 객체.** `new String(char배열)`은 배열 내용을 복사해서 String으로 봉인한다. 사람이 읽을 수 있는 글자인지는 상관없다 — `(char) 3` 같은 안 보이는 값 26개를 담아도 멀쩡한 String이다.

### 그럼 왜 배열을 String으로 포장하나? (49의 핵심)

**자바 배열의 `equals`는 내용을 안 본다. 메모리 주소만 본다:**

```java
int[] a = {1, 0, 3};
int[] b = {1, 0, 3};
a.equals(b);        // false! 내용 같아도 다른 객체라서
map.put(a, "그룹"); map.get(b);   // null! 해시맵도 둘을 다른 키로 취급
```

그래서 "eat"과 "tea"가 각각 만든 카운트 배열은 내용이 같아도 **다른 키 취급** → 그룹핑 실패. 반면 **String은 equals와 hashCode가 내용 기준**으로 구현되어 있다. `new String(keyChars)`는 결국:

> "주소로 비교되는 배열"을 → "내용으로 비교되는 String"으로 **갈아입히는 것.**

`src/_template/CharExperiment.java` 실행하면 이 세 가지를 전부 눈으로 확인할 수 있다. (면접 연결: "커스텀 객체를 HashMap 키로 쓰려면 equals+hashCode를 오버라이드해야 한다" — 배열이 그걸 안 한 대표 사례, String이 잘 한 대표 사례.)

## 5. 지금까지 수집한 패턴 ⭐

| 패턴 | 핵심 질문 | 푼 문제 |
|---|---|---|
| **보수(complement) 찾기** | "내 짝(target−현재값)을 전에 본 적 있나?"를 맵에 O(1)로 묻기 | 1 Two Sum |
| **존재 확인** | Set에 넣어보고 거절당하면 중복 | 217 |
| **카운팅** | 글자/값별 개수 세기. 한쪽 +1, 다른쪽 −1로 one-pass 가능 | 242 |
| **그룹핑 + 정규화 키** | "같은 그룹이면 반드시 같아지는 대표값"을 설계해 키로 쓰기 | 49 |

세부 메모:
- **one-pass 불변식**: "확인 → 기록" 순서를 지키면, 확인하는 시점의 맵엔 항상 **내 앞의 원소들만** 있다. 그래서 "찾은 게 나 자신인가" 검사가 원천적으로 불필요해진다. (불변식 = 루프의 매 순간 항상 참인 성질. 검사를 추가하는 것보다 불변식으로 원천 차단하는 게 한 수 위)
- **정규화 키 두 방식**: 카운팅 키("a1e1t1" 또는 고정 26칸) = O(k), 정렬 키("eat"→"aet") = O(k log k). 이론은 카운팅 승, 실측은 정렬이 이길 수도(상수가 싸서).
- **공간 복잡도 함정**: "소문자만" 제약이면 맵 키는 최대 26종 → 공간은 O(n)이 아니라 **O(1)**.
- 공통 사상: **공간을 써서 시간을 산다.** 메모리 O(n)을 내주고 시간을 O(n²)→O(n)으로. 면접에서 가장 자주 요구되는 최적화 방향.

## 6. 성능 딥다이브 🔍 (지금 안 외워도 됨. 나중에 다시 와)

- **빅오는 알고리즘을 고르는 기준, 상수는 구현을 고르는 기준.** 빅오에 안 잡히는 자잘한 비용(상수)이 실측 ms를 좌우한다. O(n log n) 정렬이 O(n) 해시맵을 실측에서 이기기도 한다(k가 작을 때).
- **beats% 판단 기준**: 내 풀이가 이론상 최적 빅오인가? → 맞으면 무시. 1~3ms 스케일에선 JVM 예열(자바가 시작 직후 느리다가 빨라지는 것)과 채점 서버 상태로 ±수십%p 튄다. 메모리%는 JVM 기본 사용량이 커서 더 노이즈.
- **박싱(boxing)**: `Map<Character, Integer>`는 원시값 char/int를 매번 Character/Integer **객체로 포장**한다. 포장 = 메모리 할당. 자바 해시맵이 느린 제1 원인. `int[26]` 배열엔 이 비용이 아예 없다.
- **사전 사이징**: 넣을 개수 n을 미리 알면 `new HashMap<>(n * 2)`. 75% 규칙 때문에 n개를 리사이징 없이 담으려면 n÷0.75 ≈ 1.33n칸 필요, 넉넉히 2n. 중간 이사(리해싱)가 사라진다.
- **키는 짧게**: 맵은 조회할 때마다 키 문자열 **전체를 훑어** 해시를 계산한다. 키가 짧고 만들기 쌀수록 빠름 → 고정 26칸 `new String(keyChars)`가 "a1e1t1"보다 유리.
- **`toCharArray()`는 배열 복사본을 만든다** — 읽기만 할 거면 `charAt(i)`가 공짜.
- **stream은 일반 for보다 무겁다** — 스트림 객체 생성 비용. 잔기술 수준.
- 실측 여정 기록: 242 HashMap 20ms → int[26] 1~3ms대. 49 putIfAbsent+문자열키 20ms → computeIfAbsent+고정키 11ms.

## 7. Git 최소 세트 ⭐ (2026-08-01 밤에 실제로 쓴 것들)

- **스테이징** = 커밋에 담을 것을 고르는 대기줄. `git add <파일>`로 담고, `git reset`으로 전부 뺀다 (파일 내용은 안 건드림. "대기줄에서 빼기"일 뿐).
- **`git commit --amend`** = 직전 커밋 고치기. 새 커밋을 만드는 대신 **방금 그 커밋에 지금 스테이징된 변경을 합치고**, 메시지도 바꿀 수 있다. 실제 사용: 커밋 직후 242를 int[26]로 고쳤을 때, 커밋을 2개로 쪼개지 않고 amend로 합쳤다.
  - ⚠️ **푸시 전에만 자유롭게.** 푸시한 커밋을 amend하면 역사를 다시 쓰는 거라 원격과 어긋난다.
- **`git rm -r --cached <경로>`** = 파일은 디스크에 두고 git 추적에서만 제거. .idea/를 뺄 때 썼다.
- 오늘 흐름 전체: `add -A` → `commit` → (242 수정) → `add` → `commit --amend`
