# 개념 정리 노트

문제 풀며 배운 개념 누적 정리. **⭐ = 필수(먼저 소화)**, **🔍 = 딥한 최적화(급하면 스킵하고 나중에 와도 됨)**.

목표: 2026-08-09까지 50개념 채우고 5분류(프로세스, 자료구조, 알고리즘/패턴, 복잡도, 자바)로 재편한다.

## 1. 문제 풀이 6단계 ⭐

문제를 열자마자 코딩부터 시작하면 안 된다. 요리로 치면 레시피도 안 읽고 불부터 켜는 것이다. 아래 6단계를 순서대로 밟는다. 1~3단계는 "문제 읽기", 4~5단계는 "풀이 설계", 6단계는 "검증"이다. **읽기가 끝나기 전에 설계를 시작하지 않는 것**이 핵심 규칙이다.

### 1단계. 입출력 정의: "뭘 받아서 뭘 돌려주는 거지?"

당연해 보이지만 여기서 이미 중요한 결정이 갈린다. 1 Two Sum이 좋은 예다.
- 반환하는 게 "두 수의 **값**"이 아니라 "두 수의 **인덱스**(몇 번째 칸인지)"다.
- 인덱스를 반환해야 한다 → 배열을 정렬하면 인덱스가 뒤섞인다 → "정렬은 못 쓰겠구나"라는 판단이 코딩 전에 나온다.
- 인덱스를 나중에 알아야 한다 → "인덱스를 어딘가 보관해야겠구나"도 여기서 나온다.

반환형 하나만 정확히 봐도 설계의 절반이 정해진다.

### 2단계. 제약 조건 읽기: 출제자가 미리 알려주는 힌트

LeetCode 문제 페이지 맨 아래 **Constraints**(제약 조건) 항목. 대부분 안 읽고 넘어가는데, 사실 여기가 정보 밀도가 제일 높다. 제약 조건은 세 종류의 정보를 준다.

**① 값의 범위** (예: `-10^9 <= nums[i] <= 10^9`)
- 마이너스가 보이면 **음수가 들어온다.** "값은 양수겠지" 같은 상상 금지.
- 값이 10억까지 크면 "값을 배열 칸 번호로 쓰는 방법"(카운팅 배열)은 불가능하다. 10억 칸짜리 배열은 못 만든다. 해시맵을 쓰라는 신호다.
- 반대로 "소문자 알파벳만"이면 종류가 26개뿐이다. 배열로 셀 수 있다는 신호다.

**② 입력 크기** (예: `n <= 10^4`)
이건 **시간 예산표**다. 컴퓨터가 1초에 대략 1억 번(10^8) 연산한다고 잡으면:

| n의 최대 | 총 연산 횟수 계산 | 결론 |
|---|---|---|
| 10^4 (1만) | O(n²)이면 10^8 | 아슬아슬 통과. 브루트포스도 되긴 함 |
| 10^5 (10만) | O(n²)이면 10^10 | 100초. 탈락. O(n log n) 이하로 풀라는 뜻 |
| 10^6 (100만) | O(n log n)이면 약 2×10^7 | 이 정도까지만 허용 |

n만 봐도 "출제자가 어떤 복잡도의 풀이를 기대하는지" 역산이 된다.

시간 예산과 짝을 이루는 **메모리 예산**도 있다. int 하나 = 4바이트가 기준이다:

| 배열 크기 | 메모리 | 판정 |
|---|---|---|
| 10^6 (100만 칸) | 4MB | 여유 |
| 10^8 (1억 칸) | 400MB | 채점 환경(수백 MB 제한)의 한계선 |
| 10^10 (100억 칸) | 40GB | 선언하는 순간 OutOfMemoryError |

`new int[100001][100001]`이 안 되는 이유가 이것이다(347에서 직접 겪음). 100001 × 100001 ≈ 10^10칸 × 4바이트 = 40GB. "2차원 배열 크기 = 행 × 열"을 곱해보는 습관이 있어야 잡히고, 곱이 10^8을 넘으면 그 설계는 폐기다.

**③ 보장 사항** (예: "정답은 정확히 하나 존재한다")
"정답이 없으면 어쩌지?", "정답이 여러 개면 뭘 반환하지?" 같은 걱정을 안 해도 된다는 공식 약속. 예외 처리 범위가 줄어든다.

> **실수 사례 (1 Two Sum에서 직접 겪음):** `if (nums[i] <= target)` 필터가 `nums=[-2,-3], target=-5`에서 두 원소를 모두 걸러서 빈 배열을 반환했다. "target보다 큰 수는 짝이 될 리 없다"는 가정은 값이 전부 양수일 때만 참이다. 음수 세계에선 `-2 + -3 = -5`처럼 target(-5)보다 큰 두 수가 짝이 된다. **제약 조건에 근거가 없는 필터/가지치기(경우의 수 쳐내기)는 금지.** 게다가 그 필터는 맞았어도 복잡도를 못 바꾸는(어차피 O(n)) 최적화였다. 이득 없이 위험만 추가한 셈이다.

### 3단계. 예제를 손으로 풀어본다: 예제는 함정 경고장이다

예제는 "문제 이해했나 확인용"이 아니다. **출제자가 일부러 함정 케이스를 예제에 심어둔다.** 1 Two Sum의 예제 3번이 `[3,3], target=6`인 건 우연이 아니라 "중복 값 조심해"라는 경고다. 예제를 손으로 따라가며 "내 방식이 이 케이스에서 정확히 뭘 하지?"를 시뮬레이션한다. 여기서 발견한 함정이 6단계의 테스트 케이스가 된다.

### 4단계. 브루트포스 먼저 + 복잡도 (⭐⭐ 내 최대 약점, 집중)

**브루트포스(brute force, 무식하게 다 해보기)** 는 특정 기법의 이름이 아니라, 이 질문의 답이다:

> **"문제의 정의를 그대로, 아무 머리도 안 쓰고 확인하려면, 뭘 다 해봐야 하지?"**

세 문제로 연습:

| 문제 | 정의 그대로 확인하려면? | 복잡도 |
|---|---|---|
| 1 Two Sum: "합이 target인 쌍이 있나" | 모든 쌍을 만들어 더해본다 | 쌍의 개수 = O(n²) |
| 217: "같은 두 원소가 있나" | 모든 쌍을 비교해본다 | 역시 모든 쌍 = O(n²) |
| 242: "t는 s를 재배열한 건가" | s의 글자 하나마다 t 전체를 뒤져 지워본다 | 글자 n개 × 매번 n칸 = O(n²) |

패턴: **"~한 게 있나?"류 문제의 브루트포스는 거의 항상 "후보 전부 나열"이고, 후보가 쌍(2개 조합)이면 O(n²)이다.**

복잡도 계산은 규칙 하나만 기억하면 된다:

> **겹친 반복문은 곱한다.**
> - n번 도는 루프 안에 또 n번 도는 루프 → n × n = **O(n²)**
> - n번 도는 루프 안에서 매번 O(1)짜리 일(해시맵 조회 등) → n × 1 = **O(n)**
> - n번 도는 루프가 나란히 두 개(중첩 아님) → n + n = 2n = **O(n)** (상수배는 떼고 말한다)

**주의 (217에서 직접 헷갈린 것):** "브루트포스: O(n)"이라고 적었는데, O(n)은 브루트포스가 아니라 Set을 쓴 **최종 풀이**의 복잡도였다. 브루트포스(모든 쌍 비교)는 O(n²)다. 두 개는 완전히 다른 것이고, 4단계에 적을 건 전자다.

왜 굳이 브루트포스를 먼저 말하나? 두 가지 이유:
1. **기준선**: 최적화가 막혀도 돌아올 정답이 있다. 면접에서 "일단 O(n²)로는 풀립니다"라고 깔아두면 최소 점수는 확보된다.
2. **공격 목표**: 5단계는 "브루트포스의 어디가 낭비인가"를 찾는 단계다. 브루트포스가 없으면 공격할 대상도 없다.

### 5단계. 병목 찾기 → 도구 선택

**병목(bottleneck, 전체를 느리게 만드는 가장 낭비스러운 부분)** 을 지목한다. 브루트포스 코드를 머릿속에 놓고 "어느 부분이 반복적으로 쓸데없는 일을 하지?"를 찾는다.

1 Two Sum의 경우: 안쪽 루프가 하는 일은 "내 짝이 있나 배열을 처음부터 다시 뒤지기"다. 이게 낭비다. "이 '찾기'를 더 싸게 하는 도구가 있나?" → 배열 탐색 O(n)을 해시맵 조회 O(1)로 교체 → 전체가 O(n²)에서 O(n)으로.

**자료구조는 문제 보고 찍는 게 아니라 병목에서 역산해서 고른다.** 다만 솔직한 진실 하나. 이 단계는 "머리로 생각해내는" 게 아니라 **도구를 미리 알아야 나온다.** 해시맵을 모르면 해시맵이 안 떠오르는 게 당연하다. 좋은 소식은 면접 문제 대부분이 15~20개 패턴(해시맵, 투 포인터, 슬라이딩 윈도우, 스택, 이진 탐색, BFS/DFS, DP 등. src/ 폴더 구조가 그 목록)으로 커버된다는 것. 공부 = 이 도구들을 하나씩 수집해서 병목과 매칭하는 훈련이다.

### 6단계. 검증 + 복잡도 진술

코딩이 끝나면 예제 전부와 3단계에서 발견한 함정 케이스(음수, 중복, 빈 입력, 길이 다름 등)를 손으로 또는 main()으로 통과시킨다. 마지막으로 "시간 O(n), 공간 O(n)입니다"라고 소리 내어 말할 수 있어야 끝난 것이다.

## 2. HashMap / HashSet: 내부에서 무슨 일이 일어나나 ⭐

### 핵심 아이디어: "아무 키로나 즉시 접근"

배열은 "3번 칸 주세요" 하면 즉시 나온다(O(1)). 근데 칸 번호를 알아야만 쓸 수 있다. 해시맵은 이걸 확장한 것이다. **"apple 주세요"처럼 아무 키로나 즉시(평균 O(1)) 찾게 해주는 자료구조.**

### 어떻게 가능한가: 키를 칸 번호로 변환한다

해시맵의 속은 사실 그냥 배열이다(**버킷 배열**. bucket = 물건 담는 양동이 = 배열의 한 칸). 저장/조회 과정:

```
1. 키를 해시 함수에 넣어 정수를 얻는다        "apple".hashCode() → 93029210
2. 배열 크기로 나눈 나머지 = 칸 번호           93029210 % 16 → 10
3. 그 칸(버킷)에 넣거나 꺼낸다                buckets[10]
```

몇 개가 들어있든 탐색 없이 계산 한 번으로 칸에 직행하니까 O(1)이다. "키 → 숫자 → 칸 번호" 변환이 전부다.

### 충돌: 다른 키가 같은 칸에 떨어지면?

`% 16` 같은 나머지 연산이라 다른 키가 같은 칸 번호를 받을 수 있다(**충돌, collision**). 자바의 처리:
- 같은 칸에 온 항목들을 **연결 리스트로 줄줄이 매단다**(체이닝). 조회할 땐 그 줄에서 키를 하나씩 비교한다.
- 한 칸의 줄이 너무 길어지면(8개 이상) 트리 구조로 바꿔서 최악에도 O(log n)으로 방어한다.
- 그래서 **평균 O(1), 최악 O(log n)**. 면접에선 "평균 O(1)"이라고 답하면 된다.

### 리사이징: 수첩이 꽉 차면 더 큰 수첩으로

- 버킷 배열은 **기본 16칸으로 시작**한다.
- 항목 수가 칸 수의 **75%** (이 비율이 load factor)를 넘으면 배열을 **2배로 키우고, 기존 항목 전부를 새 배열에 재배치**한다(**리해싱**). 수첩을 더 큰 수첩으로 옮겨 적는 셈이다.
- 왜 전부 재배치? 칸 번호가 `해시값 % 배열크기`인데 배열 크기가 바뀌면 **모든 항목의 칸 번호가 달라지기 때문.** 항목 m개면 O(m)짜리 이사 작업이다.
- "75% 찼는지 어떻게 아나?": 세어보지 않는다. 내부 `size` 필드가 put/remove마다 ±1로 이미 세어져 있고, 문턱값(16 × 0.75 = 12)과 정수 비교 한 번으로 끝(O(1)). `map.size()`가 즉답인 이유도 같다. "변할 때마다 갱신해둔 요약을 O(1)에 읽는다", 우리 패턴들과 같은 발상이다.
- HashSet은 "값 없이 키만 있는 HashMap"이다. 내부 원리는 완전히 동일하다.

> 면접 단골 질문 "HashMap 내부 구조 설명해보세요"의 모범 답안 = 위 내용을 순서대로: **해시 함수 → 버킷 인덱스 → 충돌 처리(체이닝, 트리화) → 리사이징(16칸, 75%, 2배)**.

### 자료구조 선택 기준표 ⭐

| 상황 | 선택 | 이유 |
|---|---|---|
| 키 종류가 적고 미리 안다 (소문자 26개 등) | **배열** `int[26]` | 해시 계산도 충돌도 없는 해시맵의 상위호환. `c - 'a'`로 칸 번호 직행 |
| 키 범위가 크다 (±10^9 등) | HashMap | 배열로는 칸을 못 만드니까 |
| 값 없이 "있냐 없냐"만 필요 | HashSet | |
| 넣은 순서 유지 필요 | LinkedHashMap | |
| 키가 정렬된 상태로 필요 | TreeMap | 대신 조회가 O(log n) |

## 3. Map/Set 필수 API: 언제 뭘 쓰나 ⭐

전부 **Java 8**(2014)에서 람다와 함께 들어온 것들이다. 공통 목표는 "조회 두세 번 할 일을 한 번으로".

### `set.add(x)`는 성공 여부를 알려준다

Set은 중복을 거부한다. 그래서 `add`는 **"넣는 데 성공했나"를 boolean으로 반환**한다:

```java
exist.add(3);   // true  (새로 들어감)
exist.add(3);   // false (이미 있어서 거절됨)
```

이걸 알면 "있나 확인(contains) → 없으면 넣기(add)" 조회 2번이, "넣어보고 거절당하면 = 이미 있던 것" 조회 1번이 된다:

```java
if (!exist.add(num)) return true;   // 중복 발견!
```

### 4형제: 입력, 반환값의 의미, 성능

성능은 넷 다 같다. **버킷 조회 1번, 평균 O(1).** 차이는 "무엇을 넣고 무엇을 돌려받는가"다.

**`V getOrDefault(key, defaultValue)`**
- 입력: 키, 그리고 "없을 때 대신 받을 값"
- 반환: 키가 있으면 그 값, 없으면 defaultValue. **맵은 절대 안 바뀐다** (없어도 안 넣어줌)
- `m.getOrDefault('a', 0)` = "'a'의 개수, 없으면 0으로 쳐"

**`V putIfAbsent(key, value)`**
- 입력: 키, 넣을 값(이미 만들어져 있어야 함)
- 반환: **원래 있던 값. 없어서 새로 넣었으면 null.** 즉 "null이 나왔다 = 내 값이 들어갔다"
- 반환값을 쓰려면 null 검사가 필요해서 코드가 지저분해진다. 그래서 아래 함정처럼 get을 한 번 더 부르게 되고, 그 순간 조회 2번이 된다

**`V computeIfAbsent(key, k -> 값 만드는 람다)`**
- 입력: 키, "없을 때만 실행될 레시피"
- 반환: **지금 맵에 있는 값 그 자체** (원래 있던 것이든 방금 만든 것이든). null 검사 불필요, 바로 `.add()` 체이닝 가능
- putIfAbsent와 반환값 설계가 다른 게 핵심이다. "있던 값 또는 null"이 아니라 "무조건 쓸 수 있는 값"을 준다

**`V merge(key, value, (기존값, value) -> 합치는 람다)`**
- 입력: 키, 초기값, "이미 있으면 어떻게 합칠지" 함수
- 동작: 없으면 value를 넣고, 있으면 `람다(기존값, value)` 결과로 교체
- 반환: 최종적으로 저장된 값
- `m.merge(c, 1, Integer::sum)` = "없으면 1로 시작, 있으면 기존값 + 1". getOrDefault 카운팅(`put(c, getOrDefault(c,0)+1)`, 조회 2번)을 조회 1번으로 줄인 버전

정리: **읽기만 = getOrDefault, 만들어 쓰기 = computeIfAbsent, 누적하기 = merge.** putIfAbsent는 반환값 설계 때문에 쓸 자리가 거의 없다.

**다섯 번째 형제, `put`의 반환값** (2026-08-02, 219에서 직접 발견): `put(k, v)`은 덮어쓰기 전에 있던 값을 반환한다(없었으면 null). "이전 값을 확인하면서 동시에 갱신"이 조회 1번에 된다. 219에서 `Integer prev = map.put(nums[i], i)`로 이전 인덱스를 받아 갭을 검사한 것이 활용 예다. `!add()`(존재 확인 + 삽입)와 같은 사상: **API의 반환값을 버리지 말고 판정에 쓴다.**

### putIfAbsent의 함정 (49에서 직접 겪음)

```java
map.putIfAbsent(key, new ArrayList<>());  // ① 조회 1번째
map.get(key).add(x);                      // ② 조회 2번째
```

문제 두 개. ①과 ②가 **같은 칸을 두 번 찾아간다.** 그리고 자바는 메서드 호출 전에 인자부터 계산하므로, **키가 이미 있어도 `new ArrayList<>()`가 일단 만들어졌다 버려진다.** 항목 1만 개면 쓰레기 리스트 수천 개.

`computeIfAbsent`는 둘 다 해결한다. 칸을 한 번만 찾아가고, 두 번째 인자가 값이 아니라 **람다**("필요할 때 실행할 레시피")라서 키가 없을 때만 리스트가 만들어진다(**지연 평가**, 미리 만들지 않고 필요한 순간에 만들기). 게다가 값을 반환해줘서 `.add()`를 바로 이어 붙일 수 있다.

## 4. char와 String의 정체 ⭐

### char는 글자 옷을 입은 숫자다

자바의 `char`는 **16비트 정수**다. `'a'`라고 쓰면 실제 저장되는 건 숫자 97이다.

```java
(int) 'a'         // → 97
(char) 98         // → 'b'
(char) ('a' + 1)  // → 'b'  ('a' 다음 글자)
(char) 3          // → 화면에 안 보이는 값이지만 완전히 합법인 char
```

여기서 나오는 필수 관용구 **`c - 'a'`** = 소문자를 0~25번 칸 번호로 바꾸기('a'-'a'=0, 'b'-'a'=1, ... 'z'-'a'=25). `int[26]` 카운팅 배열의 열쇠다.

### 함정: char는 계산식에 들어가는 순간 int가 된다

`'a' + j`의 결과 타입은 char가 아니라 **int**다(자바가 자동으로 승격시킴). 그래서 `List<Character>`에 `add('a' + j)`하면 컴파일 에러가 난다. int를 Character로는 자동 변환해주지 않기 때문이다. 해결은 명시적 캐스팅:

```java
(char) ('a' + j)   // OK. 괄호로 전체를 감싸야 함
(char) 'a' + j     // 함정! 'a'만 캐스팅되고 결과는 도로 int
```

### String은 "내용으로 비교되는 불변 컨테이너"다

String의 정체는 **내부에 char 배열을 품은 불변(만든 뒤 수정 불가) 객체**다. `new String(char배열)`은 배열 내용을 복사해서 String으로 봉인한다. 사람이 읽을 수 있는 글자인지는 상관없다. `(char) 3` 같은 안 보이는 값 26개를 담아도 멀쩡한 String이다.

### 그럼 왜 배열을 String으로 포장하나? (49의 핵심)

**자바 배열의 `equals`는 내용을 안 본다. 메모리 주소만 본다:**

```java
int[] a = {1, 0, 3};
int[] b = {1, 0, 3};
a.equals(b);        // false! 내용 같아도 다른 객체라서
map.put(a, "그룹"); map.get(b);   // null! 해시맵도 둘을 다른 키로 취급
```

그래서 "eat"과 "tea"가 각각 만든 카운트 배열은 내용이 같아도 **다른 키 취급**을 받아 그룹핑이 안 된다. 반면 **String은 equals와 hashCode가 내용 기준**으로 구현되어 있다. `new String(keyChars)`는 결국:

> "주소로 비교되는 배열"을 "내용으로 비교되는 String"으로 **갈아입히는 것.**

`src/_template/CharExperiment.java`를 실행하면 이 세 가지를 전부 눈으로 확인할 수 있다. (면접 연결: "커스텀 객체를 HashMap 키로 쓰려면 equals+hashCode를 오버라이드해야 한다". 배열이 그걸 안 한 대표 사례, String이 잘 한 대표 사례.)

## 5. 수집한 패턴 ⭐

패턴은 "문제 유형별 정답 코드"가 아니라 **반복되는 병목을 죽이는 반복되는 방법**이다. 각 패턴마다 세 가지를 기억한다: 어떤 원리로 작동하나, 어떤 신호가 보이면 꺼내나, 어디까지 확장되나.

### 5-1. 보수(complement) 찾기 [1 Two Sum]

**원리.** `a + b = target`이라는 등식에서 a를 알면 b는 `target - a`로 **유일하게 정해진다.** 그래서 "합이 target인 쌍을 찾아라"(후보 n²개를 뒤지는 문제)가 "각 a마다, 정해진 값 하나(`target - a`)가 존재하는가?"(조회 n번짜리 문제)로 바뀐다. 문제의 모양 자체를 "쌍 찾기"에서 "값 존재 확인"으로 바꾸는 게 핵심이고, 존재 확인을 O(1)로 해주는 도구(해시맵)와 결합해야 완성된다.

**신호.** "두 수의 합/차가 특정 값", "짝이 되는 원소가 있는가"라는 문구. 등식으로 쓸 수 있으면 후보다.

**확장.** 3Sum(하나를 고정하면 나머지가 Two Sum이 된다), Subarray Sum Equals K(누적합 prefix[j] - prefix[i] = k에서 prefix[i] = prefix[j] - k라는 보수를 찾는다). "미지수 하나를 고정하면 나머지가 유일하게 정해지는" 구조는 전부 이 패턴이다.

### 5-2. 존재 확인 (seen set) [217]

**원리.** "전에 이걸 본 적 있나?"라는 질문에 O(1)로 답하려면, 본 것들을 기억하는 장부가 필요하다. Set이 그 장부다. 중복 판정은 별도 로직이 아니라 **Set의 "중복 거부" 성질 자체를 판정기로 쓴다**(`add`가 false면 중복). 브루트포스가 "과거를 매번 다시 뒤지는" O(n²)인 것을, "과거를 장부에 적어두고 조회"하는 O(n)으로 바꾼다. 공간 O(n)을 내주고 시간을 산다.

**신호.** "중복이 있는가", "이미 나왔는가", "처음 등장하는 것은".

**확장.** 5-1 보수 찾기도 사실 이 패턴 위에 서 있다(장부에서 보수를 조회). 방문 체크(그래프 탐색의 visited), 순환 감지도 같은 원리다.

### 5-3. 카운팅 (빈도 배열/맵) [242]

**원리.** 애너그램의 정의는 "순서만 다르고 구성이 같다"이다. 즉 순서 정보를 버리고 **"무엇이 몇 개"만 남긴 요약본**(빈도)이 같으면 된다. 카운팅은 데이터를 이 요약본으로 압축하는 행위다. 요약본끼리 비교하면 원본을 정렬하거나(O(k log k)) 반복 탐색할(O(k²)) 필요가 없다.

242의 +1/-1 one-pass는 여기서 한 발 더 나간 것이다. "t의 요약본과 s의 요약본을 각각 만들어 비교" 대신 **"두 요약본의 차이"를 직접 계산**한다. t로 +1, s로 -1 하면 남는 것은 차이 벡터고, 애너그램이면 모든 칸이 0이다.

**신호.** "구성이 같은가", "가장 많이/적게 등장하는", "k번 이상 나오는". 순서가 무의미해 보이면 후보다.

**확장.** Top K Frequent(빈도를 센 뒤 상위 k개), Ransom Note(한쪽 빈도가 다른 쪽을 덮는가). 키 종류가 적으면(소문자 26개) 맵 대신 `int[26]` 배열이 상위호환이다(섹션 2의 선택 기준표).

### 5-4. 그룹핑 + 정규화 키 [49]

**원리.** "같은 그룹"이라는 관계는 컴퓨터가 직접 다루기 어렵다. 그래서 **그룹마다 유일한 대표값(정규화된 키, canonical key)을 설계**해서 "같은 그룹인가?"를 "키가 같은가?"로 바꾼다. 키 설계의 조건은 두 방향 모두 성립해야 한다는 것:
- 같은 그룹이면 → 반드시 같은 키 (안 그러면 한 그룹이 쪼개진다)
- 다른 그룹이면 → 반드시 다른 키 (안 그러면 다른 그룹이 합쳐진다. "ab"와 "ac"가 같은 키가 됐던 버그가 이 위반)

키만 잘 만들면 나머지는 해시맵이 알아서 한다. `computeIfAbsent(키, ...)`로 키별 리스트에 던져 넣으면 그룹핑 끝.

**신호.** "~끼리 묶어라", "같은 종류별로". 반환형이 `List<List<...>>`면 강한 후보다.

**확장.** 애너그램 그룹의 키는 카운팅 요약본(5-3을 키로 재활용) 또는 정렬 결과다. 다른 문제에선 "정규화" 방법이 달라진다(예: 회전해서 같은 문자열이면 최소 회전형을 키로). **"이 그룹의 모든 멤버가 공통으로 도달하는 형태가 뭔가?"** 를 묻는 게 키 설계의 출발점이다.

### 패턴들의 공통 뼈대

네 패턴 모두 한 문장으로 압축된다: **비싼 반복 탐색을, 미리 계산해 둔 요약(장부, 빈도, 대표값)에 대한 O(1) 조회로 바꾼다. 대가는 공간 O(n).** 면접에서 "시간-공간 트레이드오프"라고 부르는 것의 실체가 이거다.

세부 메모:
- **one-pass 불변식**(invariant, 루프 내내 항상 참인 성질): "확인 → 기록" 순서를 지키면, 확인하는 시점의 맵엔 항상 내 앞의 원소들만 있다. 그래서 "찾은 게 나 자신인가" 검사가 원천적으로 불필요하다. 검사를 추가하는 것보다 불변식으로 원천 차단하는 게 한 수 위다.
- **공간 복잡도 함정**: "소문자만" 제약이면 맵 키는 최대 26종이라 공간은 O(n)이 아니라 **O(1)**이다.

## 6. 나머지 연산과 순환 인덱스 ⭐

### `%`는 나머지 연산자다

`7 % 3 = 1` (7을 3으로 나눈 나머지). 이 연산의 핵심 성질:

> **`i % n`의 결과는 무조건 0 ~ n-1 사이에 갇힌다.** i가 아무리 커져도 결과는 n을 넘지 못한다.

n=3이면 i가 커질수록 결과는 0, 1, 2, 0, 1, 2를 반복한다. 시계와 같은 원리다(13시 = `13 % 12` = 1시. 12를 넘으면 처음으로 되감긴다).

### 이미 만난 곳: 해시맵 버킷 계산

`93029210 % 16 = 10`. 해시코드가 몇억이든 `% 16` 하나로 0~15번 칸 안에 떨어진다. "아무리 큰 숫자든 배열 범위 안에 가둔다"가 이 연산의 용도다(섹션 2).

### 알고리즘 문제에서의 쓰임: 원형(circular) 순회

배열 끝에 도달하면 처음으로 되감고 싶을 때, 조건문 없이 수식으로 해결한다:

```java
for (int i = 0; i < n; i++) {
    int idx = (start + i) % n;   // start=3, n=5면: 3, 4, 0, 1, 2
}
```

원형 배열, 원형 큐, "마지막 다음은 다시 처음" 구조가 나오면 이 관용구를 꺼낸다. OS의 라운드 로빈 스케줄링(프로세스를 순서대로 돌아가며 배분)도 같은 수식 위에 서 있다. 코딩테스트에 "라운드 로빈"이라는 이름으로는 안 나오지만, 순환 인덱스 형태로는 계속 나온다.

## 7. 성능 딥다이브 🔍 (지금 안 외워도 됨. 나중에 다시 와)

- **빅오는 알고리즘을 고르는 기준, 상수는 구현을 고르는 기준이다.** 빅오에 안 잡히는 자잘한 비용(상수)이 실측 ms를 좌우한다. O(n log n) 정렬이 O(n) 해시맵을 실측에서 이기기도 한다(k가 작을 때).
- **beats% 판단 기준**: 내 풀이가 이론상 최적 빅오인가? 맞으면 무시한다. 1~3ms 스케일에선 JVM 예열(자바가 시작 직후 느리다가 빨라지는 것)과 채점 서버 상태로 ±수십%p 튄다. 메모리%는 JVM 기본 사용량이 커서 더 노이즈다.
- **박싱(boxing)**: `Map<Character, Integer>`는 원시값 char/int를 매번 Character/Integer **객체로 포장**한다. 포장 = 메모리 할당. 자바 해시맵이 느린 제1 원인이다. `int[26]` 배열엔 이 비용이 아예 없다.
- **사전 사이징**: 넣을 개수 n을 미리 알면 `new HashMap<>(n * 2)`. 75% 규칙 때문에 n개를 리사이징 없이 담으려면 n÷0.75 ≈ 1.33n칸이 필요하고, 넉넉히 2n으로 잡는다. 중간 리해싱이 0번이 된다.
- **키는 짧게**: 맵은 조회할 때마다 키 문자열 전체를 훑어 해시를 계산한다. 키가 짧고 만들기 쌀수록 빠르다. 고정 26칸 `new String(keyChars)` 키가 "a1e1t1"보다 유리한 이유다.
- **`toCharArray()`는 배열 복사본을 만든다.** 읽기만 할 거면 `charAt(i)`가 공짜다.
- **stream이 for문보다 느린 이유**: 세 가지 비용이 겹친다.
  1. **설치 비용**: `stream()`을 부르는 순간 Stream 객체, 분할자(spliterator), 람다 객체들이 먼저 만들어진다. 컨베이어 벨트를 설치하고 나서야 물건이 흐르는 구조라, 원소가 적으면 설치비가 본작업보다 크다. for문은 설치할 게 없다.
  2. **원소당 통행료**: for문의 몸통은 기계어로 바로 붙지만, stream은 원소 하나마다 람다 호출(메서드 호출)을 거친다. JIT(자바가 실행 중에 자주 도는 코드를 기계어로 최적화하는 장치)가 결국 비슷하게 만들어주긴 하는데, 그 전까지는 호출 비용을 문다.
  3. **예열 부족**: JIT 최적화는 코드가 수천 번 돌아야 발동한다. LeetCode처럼 짧게 돌고 끝나는 환경에선 stream이 최적화되기 전에 채점이 끝난다. for문은 최적화가 필요 없을 만큼 단순해서 처음부터 빠르다.
  - 결론: 원소 26개짜리 마지막 검사에서 체감 차이는 마이크로초 수준이다. LeetCode ms 싸움에서만 의미 있고, 실무에선 가독성으로 stream을 고르는 경우도 많다.
- 실측 기록: 242는 HashMap 버전 20ms에서 `int[26]` 버전 1~3ms대로 (LeetCode 제출 기준). 49는 putIfAbsent+가변 문자열 키 20ms에서 computeIfAbsent+고정 26칸 키 11ms로.

## 8. 에러의 두 종류 ⭐ (347에서 둘 다 겪음)

- **컴파일 에러**: 실행 전에 javac가 거부. "cannot find symbol" = 그 이름을 모른다는 뜻이고, 클래스명이면 대부분 **import 누락**이다(`SortedMap`, `TreeMap`은 `java.util`에 있다). 오타, 타입 불일치도 여기.

- 읽는 순서: 예외 이름 → 메시지의 숫자 → 스택 트레이스의 내 코드 줄 번호.

## 9. 자바 메모리 기초 (2026-08-02 문답에서) ⭐

- **참조(reference)**: 객체 변수와 객체 배열의 칸에는 객체 자체가 아니라 **객체가 힙 어디에 사는지 주소**가 들어간다. HashMap 버킷 배열의 칸이 담는 것도 첫 Node의 참조다.
- **배열 초기화 규칙**: `new`로 만든 배열은 전 칸이 0비트로 청소되어 나온다. 프리미티브 칸에서는 0(int), false(boolean), 0.0(double)으로 읽히고, 객체 배열 칸에서는 **null**(주소 없음)로 읽힌다. `new int[10]`이 전부 0이었던 이유. 빈 버킷에 미리 만들어둔 Node가 없는(= null인) 이유이기도 하다.
- **힙 메모리와 GC**: `new`로 만드는 모든 것(배열, 객체)은 힙(heap)이라는 창고에 산다. 아무도 참조하지 않게 된 객체(리해싱 후 버려진 옛 배열 등)는 가비지 컬렉터가 수거한다. 주의: 자료구조 힙(우선순위 큐의 그 힙)과 이름만 같고 완전 다른 것.
- **"크기가 늘어나는" 자료구조의 실체**: 배열은 크기 고정이다. HashMap도 ArrayList도 커지는 게 아니라 **더 큰 배열을 새로 할당하고 옮겨 담은 뒤 옛것을 버린다.** 차이는 이사 방식이다. HashMap은 칸 번호가 `% 배열크기`라 전원 재계산(리해싱, 2배씩), ArrayList는 칸 번호가 "몇 번째"라 자리 그대로 복사만(1.5배씩, 100% 차면).
- **ArrayList vs LinkedList**: ArrayList는 한 줄로 붙여 저장해서 get(i)가 O(1), 대신 꽉 차면 이사. LinkedList는 노드가 흩어져 살며 next 참조로 연결되어 이사가 없지만 get(i)가 O(n). 트레이드오프가 정반대.
- **충돌 해결 두 학파**: 체이닝(같은 칸에 연결 리스트로 줄 세우기, 자바 HashMap 방식, 8개 넘으면 트리화) vs 개방 주소법(옆 칸 찾아가기, 선형 탐사 등. 학부 때 배운 "여러 전략"이 이쪽).
- **HashMap null 키**: 딱 1개 허용. null은 hashCode()를 못 부르니 0번 버킷에 특별 취급으로 저장 (각주 수준).

## 10. 배열과 ArrayList 딥다이브 (2026-08-03 문답 15문항) ⭐

### 배열의 메모리 실체
- 배열 = 힙에서 `헤더 + 원소크기 × 길이`를 **한 덩어리로 연속 할당**받은 것. `new int[10]`이 전부 0인 이유(0비트 청소)가 한 번의 연속 쓰기로 가능한 것도 이 덕분이다.
- 주소 공식: **`addr(a[i]) = B + i × 원소크기`** (B = 데이터 시작 주소). 곱셈 1번 + 덧셈 1번, i와 무관 → 인덱싱 O(1). 성립 전제는 연속 할당 + 원소 크기 균일.
- 인덱스의 정체는 "몇 번째"가 아니라 **"몇 개를 건너뛰는가"(오프셋)**. a[0] = 0개 건너뜀 = 시작점. 0-인덱싱은 관습이 아니라 주소 공식의 필연이다.
- 배열 끝 바로 뒤 바이트는 이미 남의 땅일 수 있다 → 제자리 확장 불가 → **크기 고정.** O(1) 인덱싱(축복)과 크기 고정(저주)은 같은 연속성의 양면이다.

### 스택 vs 힙
- `int[] a = new int[10]`: 변수 `a`(참조 8B)는 **스택 프레임**에, 본체(헤더+40B)는 **힙**에. 배열이 몇 칸이든 a는 8B다.
- `int[] b = a`가 복사하는 건 참조뿐. 힙 덩어리는 하나, 화살표만 둘. 메서드에 배열을 넘겨도 같다(헬퍼가 원본을 고치는 이유).
- 수명: 스택 프레임은 리턴 시 즉시 소멸, 힙 본체는 참조가 끊긴 뒤 GC가 "내킬 때" 수거.
- 에러 쌍: **힙 부족 = OutOfMemoryError**(new 과다), **스택 부족 = StackOverflowError**(재귀 과다).
- 참조 크기: 64비트 = 주소가 64비트 숫자라는 뜻이라 원칙 8B. 힙 32GB 미만이면 JVM이 4B로 압축(compressed oops) → 어림은 4~8B. (32비트 시대 램 4GB 한계 = 2^32개 주소가 전부라서)

### 프리미티브 배열 vs 객체 배열, 그리고 캐시
- **int[] = 값이 나란히 / Integer[] = 참조만 나란히, 본체는 힙에 산개.** 객체 배열 칸에 본체가 못 들어가는 이유: 주소 공식은 원소 크기 균일이 전제인데 객체 크기는 제각각.
- 워드 = CPU가 연산하는 단위(64비트 CPU에서 8B). **캐시 라인 = 메모리에서 캐시로 운반하는 단위(64B).** 다른 층의 단위다.
- int[] 순회: 64B 로드 한 번에 값 16개, 순차 접근이라 프리페치도 작동. Integer[] 순회: 64B에 주소 8개뿐, 값을 읽으려면 참조마다 산개한 본체로 점프 → 점프마다 캐시 미스 가능(캐시 ~1ns vs 램 ~100ns).
- 이것이 `Arrays.sort(int[])`(O(n log n))가 HashSet 풀이(O(n))를 실측에서 이기는 단가 차이의 실체다: 실측 시간 = 연산 횟수 × 연산 단가.

### 2차원 배열의 실체
- `new T[r][c]` = "배열의 배열". 바깥 배열엔 행 **참조** r개, 행들은 힙에 각각 독립된 배열로 산다. 그래서 행 길이가 제각각인 jagged 배열(`new int[3][]`)도 합법.
- `new Integer[100001][100001]` 정산: 바깥(참조 10^5개 ≈ 0.8MB) + 행 배열들(0.8MB × 10^5 ≈ 80GB, 압축 참조면 40GB). 전부 null인 상태로 이 크기다. Integer 본체는 하나도 없이.

### ArrayList 내부와 분할 상환
- 필수 필드는 둘: `Object[] elementData`(실저장소 참조), `int size`(논리적 원소 수). capacity는 필드가 아니라 `elementData.length`다(배열이 자기 길이를 아니까 중복 저장 안 함).
- size ≠ capacity: capacity 10, size 3인 리스트에 get(5) 하면 칸은 있어도 IndexOutOfBounds(경계 검사는 size 기준).
- 꽉 찬 상태의 add: ① 1.5배 새 배열 힙에 할당 ② 전부 복사 ③ 삽입 ④ 옛 배열은 GC 대상. 그 한 번은 O(n).
- **성장 전략 재판** (직접 유도):
  - +10씩(덧셈 성장)이면: 복사량 10+20+...+n = 10 × 가우스 합 ≈ 5×10^8회(n=10^5) → 총 O(n²), 예산표로 약 5초. 사형.
  - ×1.5(곱셈 성장)이면: 총 복사 = n(1 + 2/3 + 4/9 + ...) = n × 1/(1−2/3) = **3n** → 총 O(n), add 1회 평균 O(1).
  - **분할 상환(amortized) O(1)**: 개별 연산은 가끔 O(n)이지만 n회 총 비용이 O(n)이라 평균은 상수. HashMap의 2배 리사이징도 같은 논증(공비 1/2, 총 2n).
  - 한 줄: **곱셈 성장 → 등비 합 → 총 O(n) / 덧셈 성장 → 등차 합(가우스) → 총 O(n²).**
- capacity 역산 (본인 유도 보존): 10 × 1.5^x ≥ 10^5 → x ≥ 4/log(1.5) = 4/0.176 ≈ 22.7 → x = 23 → capacity ≈ 112,227 (실제 정수 나눗셈 수열로는 106,710). 실측 확인은 `src/_template/CapacityGrowth.java`.

### 박싱 대차대조표
- `ArrayList<Integer>`에 int 10^5개 담기 (본인 정산): 참조 112,227 × 8B ≈ 0.9MB + Integer 본체 10^5 × 16B(헤더 12~16B + 값 4B) = 1.6MB → **약 2.5MB, int[](400KB)의 6배.**
- int 4B 하나의 실비용 ≈ 참조 8B + 본체 16B + capacity 슬랙 = **약 25B.** 코딩테스트에서 프리미티브 배열로 버틸 수 있으면 컬렉션 대신 배열.

### Integer 캐시와 == 함정
- 자바는 **-128~127의 Integer를 미리 만들어 캐싱**한다. `Integer a = 8`은 `Integer.valueOf(8)`이라 캐시된 같은 객체를 받는다.
- 그래서 `a == b`(주소 비교)가 127까지는 true, 128부터 false. 면접 전설의 함정. 실무 규칙: **Integer 비교는 무조건 equals.**

### 제네릭 배열 금지의 논증
- 배열은 공변이라(`Object[] o = new Integer[10]` 합법) 잘못된 저장을 **런타임 태그 검문**으로 막는다(ArrayStoreException).
- 제네릭은 반대: **컴파일 때 전부 검사**하고 꺾쇠 정보를 지운다(타입 소거). 런타임엔 검사할 정보도, 필요도 없다.
- | | 컴파일 | 런타임 | / 배열: 느슨 | 엄격(태그 검문) / 제네릭: 엄격 | 노체크(소거)
- `new ArrayList<Integer>[n]` 금지 이유: 배열의 검문 의무는 있는데 꺾쇠 정보가 지워져 검문 불가 = 지킬 수 없는 계약. raw `new ArrayList[n]`은 클래스 레벨 검문("ArrayList인가")은 지킬 수 있어 허용하되, 꺾쇠 검증 포기 서명(unchecked 경고)을 받는다.
- 소거가 지우는 건 꺾쇠 안뿐이다. 클래스 자체는 런타임에 살아있다(instanceof, getClass 동작).

### 밀집 vs 희소 판정식
- 밀집(배열): 메모리 `n × 원소크기`, 접근 O(1) 확정에 상수 최저. 희소(맵): 메모리 `m × 엔트리비용(≈32B+)`, 접근 평균 O(1)에 상수 큼.
- **boolean[] 기준: 점유율 m/n > 1/32 ≈ 3%면 배열이 메모리에서도 승.**
- 347 재판: count 종류 m ≤ √(2n) ≈ 450 (서로 다른 count의 합 ≥ 가우스 합이라는 논증), 점유율 0.45% < 3% → 희소 승. 실측과 일치.
